# Модель безопасности

Time Toolkit работает с содержимым личных, учебных и корпоративных сообщений.
Главные риски — утечка токена, отправка не в тот профиль или канал, случайное
изменение read state и сохранение сообщений там, где их не должно быть.

## Границы доверия

Time Toolkit доверяет локальному пользователю и процессам, которым он сам дал
доступ к CLI, MCP или HTTP-ключу. Инструмент не изолирует враждебный код,
запущенный под той же учётной записью ОС: такой код может читать переменные
окружения, обращаться к локальным процессам и притвориться подтверждённым
Python-клиентом.

Правила `write_mode` защищают от случайной автоматизации. Это не песочница и не
замена правам Time, allowlist внешнего сервиса или системной политике компании.

## Секреты

Профиль содержит настройки, но не токен. `SecretStore` ищет секрет в таком порядке:

1. `TIME_TOOLKIT_<PROFILE>_TOKEN` и при необходимости `..._CSRF`;
2. системный keyring под service name `dev.erstcl.time-toolkit`.

Ключ локального HTTP API хранится отдельно или приходит через
`TIME_TOOLKIT_SERVICE_API_KEY`.

Нельзя:

- передавать токен параметром CLI: он попадёт в историю shell и список процессов;
- вставлять токены, cookies и CSRF в сообщения, логи, issues, fixtures и commits;
- хранить реальные ответы API или экспорт сообщений в репозитории;
- печатать окружение целиком в CI, если в нём есть секреты;
- давать HTTP-ключ процессу, которому не нужны сообщения из Time.

Логи `--debug` содержат HTTP-метод и URL, но не заголовки авторизации. Результаты
команд могут содержать полные тексты сообщений, email, имена, permalink и
метаданные файлов. Перенаправление stdout в файл создаёт новый набор чувствительных
данных, за который отвечает вызывающий процесс.

`RealtimeService` загружает токен в тот же Python-процесс, где работает consumer.
Если consumer или solver не должен иметь доступ к токену, используйте отдельный
gateway-процесс `timetk -o ndjson watch`: только gateway читает `SecretStore`, а
следующий процесс получает отфильтрованные события через stdout или защищённую
локальную очередь. Локальная политика `readonly` блокирует штатные методы записи,
но не уменьшает серверные права самого session token.

## Профили и запись

Любая операция, меняющая Time, требует явного профиля. Профиль по умолчанию
применяется только там, где команда это допускает; для записи молчаливой подмены
нет.

| Способ записи | `readonly` | `approval` | `fullauto` |
|---|---:|---:|---:|
| CLI с вопросом `Proceed?` | запрещён | после ответа | после ответа |
| CLI с `--dry-run` | только preview | только preview | только preview |
| CLI с `--yes` | запрещён | запрещён | разрешён |
| MCP `prepare` → подтверждение → `commit` | запрещён | разрешён | разрешён |
| Python, `write_mode="automated"` | запрещён | запрещён | разрешён |
| Python, `write_mode="confirmed"` | запрещён | доверенный flow | доверенный flow |
| HTTP API | отсутствует | отсутствует | отсутствует |

Политика меняется только явной operator-командой:

```bash
timetk profile update PROFILE --write-policy readonly
timetk profile update PROFILE --write-policy approval
timetk profile update PROFILE --write-policy fullauto
```

Проверка повторяется непосредственно перед каждой записью в `TimeService`. MCP
дополнительно требует человеческое подтверждение даже при `fullauto`. Значение
`confirmed` — утверждение доверенного вызывающего кода, а не доказательство, поэтому
произвольный локальный Python-процесс не считается изолированным security boundary.

Внешняя интеграция обязана сама ограничить получателей. Time Toolkit не знает её
пользователей, бизнес-правила и область ответственности, поэтому общий allowlist
в пакет не встроен.

## Подтверждение MCP

MCP разбивает запись на два инструмента. `time_prepare_write` создаёт полный план и
одноразовую фразу `CONFIRM <operation_id>`, но ничего не меняет. Клиент показывает
план человеку. Только после отдельного согласия он вызывает
`time_commit_write`.

Подготовленная операция:

- хранится только в памяти процесса MCP;
- действует 600 секунд;
- привязана к профилю, серверу, действию, адресату и содержимому;
- удаляется при успешном claim до сетевого вызова;
- не может использоваться повторно после попытки выполнения.

Перезапуск MCP удаляет все подготовленные операции. Согласие на одну операцию не
переносится на следующую.

## Чтение и read state

Команды чтения используют семантически read-only Mattermost endpoints. Некоторые
batch/search операции в Mattermost имеют HTTP-метод POST, но они не вызывают
`view channel` или `set unread`. Просмотр через CLI, MCP, Python, HTTP или `watch`
не должен менять счётчики Time.

Состояние меняют только явно названные операции `mark-read` и `mark-unread`. Они
считаются записью и проходят ту же политику подтверждений.

## Сеть

Профили с внешним сервером обязаны использовать HTTPS. HTTP разрешён только для
`localhost`, `127.0.0.1` и `::1`. TLS проверяется системным trust store; отключения
проверки сертификата нет.

HTTP-адаптер по умолчанию слушает только `127.0.0.1`. Для другого интерфейса нужен
`--allow-network`, но этот флаг не добавляет TLS, firewall, rate limit или
аутентификацию пользователей. Публиковать адаптер напрямую в сеть нельзя. Если
удалённый доступ действительно нужен, ставьте перед ним TLS reverse proxy,
сетевые ограничения и отдельную аутентификацию либо используйте private network.

WebSocket принимает рекламируемый сервером URL только с допустимой схемой и без
credentials, query или fragment. Тот же hostname и port разрешены автоматически.
Другой endpoint должен быть явно указан в `allowed_websocket_hosts`; HTTPS нельзя
понизить до `ws://`. До allowlist-проверки токен на рекламируемый host не
передаётся. Сертификат проверяется так же, как для REST.

## Компрометация и ротация

Если токен мог попасть в лог, чат, снимок экрана или репозиторий:

1. отзовите сессию или personal access token в Time;
2. удалите локальный секрет командой `timetk -p PROFILE auth clear`;
3. создайте новый токен и сохраните через `auth set`;
4. проверьте историю Git, CI artifacts, shell history и логи потребителя;
5. если утёк HTTP-ключ, выполните `service-key clear`, затем `service-key create`;
6. считайте ранее скачанные сообщения скомпрометированными и удалите их из
   неразрешённых хранилищ.

Простое удаление секрета из последнего commit не убирает его из истории Git.
Ротация обязательна даже после переписывания истории.

## Перед подключением нового сервиса

Проверьте, что сервис получает только нужный профиль, не логирует stdout, задаёт
ограничение объёма и срока хранения, не пересылает текст сторонним моделям без
разрешения и имеет свой allowlist для автоматических записей. Запускайте его под
отдельной учётной записью или в контейнере, если процессы не должны иметь общий
доступ к Keychain.
